# Phase 0 Research: 多车网格调度演示

Date: 2026-09-29 | Feature: 001-multi-vehicle-dispatch

Technical Context 无 NEEDS CLARIFICATION 项；以下为关键技术决策的研究结论。

## R1. 多车防碰撞机制

**Decision**: 时空预约表（Space-Time Reservation Table）+ 逐格移动确认（WHCA* 的简化单窗口版）。

- 网格维护 `reserved[cell, tick]` 集合：车辆规划路径时把未来各 tick 占用的格子写入预约。
- 车辆每个 tick 移动前检查下一格的预约：已被他车预约/占据 → 原地等待并重新预约。
- 允许"跟随"（前车刚离开的格子下一 tick 可用），保证车流吞吐；对向会车因预约冲突自然形成等待。
- **Rationale**: 实现简单（纯内存 dict）、可证明零碰撞（预约互斥即格互斥）、天然产生"路径重合→等待"的规格行为；相比 CBS/MAPF 求解器，无需外部求解器、代码量小一个数量级，符合章程 YAGNI。
- **Alternatives considered**:
  - CBS (Conflict-Based Search)：最优解但实现复杂、100 车规模计算量大，演示场景过度设计；
  - 纯反应式避障（无预约）：高速车流下易产生活锁/对峙，难以保证零碰撞的可验证性。

## R2. 路径规划

**Decision**: 标准 A*（4 邻接、曼哈顿启发式），规划时把"当前障碍物 + 他人对目标格的静态预约"视为不可通行。

- 高度差场景不存在，4 邻接足够；对角穿行会造成碰撞判定歧义，禁用。
- 车辆每逢以下情况重新规划：任务下达、前方被堵超过阈值 tick、障碍物变更影响剩余路径。
- 200×200 的 A* 单次最坏 ~40k 节点，Python 可行（<50ms）；用增量触发 + 每 tick 限流重规划次数控制 CPU。
- **Rationale**: A* 是该规模网格的标准解；预约冲突的动态性交给 R1 的逐 tick 确认兜底，规划器无需做完整时空搜索。
- **Alternatives considered**: D* Lite（动态重规划更快但实现复杂度高，收益在频繁地图变更时才明显）；BFS（无启发式，200×200 下偏慢且路径质量差）。

## R3. 死锁避免与恢复

**Decision**: 三层策略——预防、检测、恢复。

1. **预防**：任务目标格下达前预约终点；规划时禁止把路径终点停在他车必经窄通道内（空闲车主动靠边不挡道）。
2. **检测**：车辆连续 N tick（折算 ~15s）位置未变且非正常等待终点 → 标记 `stalled`；多车互相构成等待环 → `deadlock` 候选。
3. **恢复**（按代价递增）：a) 受阻车重规划绕行；b) 让路——挡路空闲车收到让路指令，移向邻近空格；c) 改派——把任务回收重派给其他车；d) 兜底——虚拟"相位放行"（短暂冻结部分预约按序放行）。
- **Rationale**: "尽量避免 + 可自动恢复"符合规格（FR-012）；分层恢复保证多数冲突用最低代价手段解决。
- **Alternatives considered**: 全局死锁求解器/拓扑排序解锁：正确性证明复杂，演示场景收益低。

## R4. 任务生成与均匀分配

**Decision**: 双队列 + 最少负载优先（least-loaded）分配 + 随机抖动。

- 任务成对生成（1:1 入库/出库，FR-018）：出库任务随机选一个"有料箱的存储点位"，入库任务随机选一个"空存储点位"。
- 分配：每次选当前累计任务数最少的车（平局随机），数学上保证任意两车差 ≤1，远优于 ±20% 约束；同时任务点位随机散布。
- **Rationale**: least-loaded 是保证均匀性的最简构造，无需复杂均衡器。
- **Alternatives considered**: 纯随机分配（需要事后补偿才能满足 ±20%）；拍卖/竞标机制（过度设计）。

## R5. 仿真与前端通信架构

**Decision**: 单进程 asyncio 仿真引擎（固定 10 tick/s）+ FastAPI WebSocket 增量推送 + Canvas 2D 分层渲染。

- 引擎每 tick 产出增量（位置变化的车/箱、状态变化、指标），WS 下发 ≤100ms。
- 前端三层 Canvas：静态层（网格+货架+站点，只画一次）、障碍层（障碍物变更时重绘）、动态层（料箱+小车，每帧重绘）。
- 小车在格间移动做线性插值以获得连续高速观感（渲染层插值，逻辑层仍逐格）。
- **Rationale**: 单进程避免序列化/进程通信复杂度；增量推送使 100 车 @10tick/s 的带宽可忽略；分层 Canvas 保证 40k 格子下 ≥30fps。
- **Alternatives considered**: SSE/轮询（延迟与带宽差）；WebGL（40k 静态格 + 100 动态实体用不上）；多进程仿真（单机演示无必要，违背 YAGNI）。

## R6. 布局参数（固定布局，FR-016/FR-017）

**Decision**: 200×200 地图按以下固定布局初始化：

- 货架区：地图中部，行 60..139 × 列 40..159，每 2 行货架行（存储点位）之间留 2 行通道；点位间隔 1 列通道——约 40 行点位 × 60 列点位 = 2400 个存储点位，半仓 ~1200 料箱。
- 入库口：地图西侧边缘中部（行 95..104，列 0..4 区域）；出库口：东侧边缘中部（行 95..104，列 195..199）。两站不同侧，车流自然分流。
- 边界格不可通行。
- **Rationale**: 通道宽度 2 格可容纳对向排队等待（规格 US3 场景 3）；2400 点位提供充足的随机目标多样性，1200 料箱对渲染无压力（动态层仅绘制有料箱的点位）。

## R7. 验证环境（docker rcs_core_dev）

**Decision**: 仿真本体为纯 Python + 浏览器，可在宿主机直接运行；容器内验证步骤写入 quickstart：
`docker exec -it cuda12_8_torch_2_9_1_core_dev bash -c "cd /home/dev/workspace/binglee/rcs_demo && ..."`
（host 网络模式，容器内启动的端口宿主机直接可访问）。
- **Rationale**: 容器为 host 网络，演示服务在容器内启动即可从宿主机浏览器访问；`--check` 自检不依赖 GPU/ROS，任何环境可跑。

## R8. 测试策略

**Decision**: 缩尺快速回归（pytest）+ 演示级冒烟。

- 单元：A* 可达性/绕障、预约互斥、布局约束。
- 集成（缩尺 40×40 / 10 车 / 加速时钟）：跑 N tick 断言 ① 零同格碰撞 ② 分配偏差 ≤±20% ③ 注入围堵后 M tick 内恢复移动。
- 冒烟：`--check` 验证导入、布局生成、规划器自测、API 可绑定。
- **Rationale**: 200×200×100 车全量跑 30 分钟不适合 CI；缩尺模型与全量共享同一引擎代码，保证断言有效性。
