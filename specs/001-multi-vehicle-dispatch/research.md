# Phase 0 Research: 多车网格调度演示

Date: 2026-09-29 | Feature: 001-multi-vehicle-dispatch

Technical Context 无 NEEDS CLARIFICATION 项；以下为关键技术决策的研究结论。

## R1. 多车防碰撞机制

**Decision**: 时空预约表（Space-Time Reservation Table）+ 逐格移动确认（WHCA* 的简化单窗口版）。

- 网格维护 `reserved[cell, tick]` 集合：车辆规划路径时把未来各 tick 占用的格子写入预约。
- 车辆每个 tick 移动前检查下一格的预约：已被他车预约/占据 → 原地等待并重新预约。
- 允许"跟随"（前车刚离开的格子下一 tick 可用），保证车流吞吐；对向会车因预约冲突自然形成等待。
- **Rationale**: 实现简单（纯内存 dict）、可证明零碰撞（预约互斥即格互斥）、天然产生"路径重合→等待"的规格行为；相比 CBS/MAPF 求解器，无需外部求解器、代码量小一个数量级，符合章程 YAGNI。
- **Alternatives considered**:
  - CBS (Conflict-Based Search)：最优解但实现复杂、100 车规模计算量大，演示场景过度设计；
  - 纯反应式避障（无预约）：高速车流下易产生活锁/对峙，难以保证零碰撞的可验证性。

## R2. 路径规划

**Decision**: 标准 A*（4 邻接、曼哈顿启发式），规划时把"当前障碍物 + 他人对目标格的静态预约"视为不可通行。

- 高度差场景不存在，4 邻接足够；对角穿行会造成碰撞判定歧义，禁用。
- 车辆每逢以下情况重新规划：任务下达、前方被堵超过阈值 tick、障碍物变更影响剩余路径。
- 200×200 的 A* 单次最坏 ~40k 节点，Python 可行（<50ms）；用增量触发 + 每 tick 限流重规划次数控制 CPU。
- **Rationale**: A* 是该规模网格的标准解；预约冲突的动态性交给 R1 的逐 tick 确认兜底，规划器无需做完整时空搜索。
- **Alternatives considered**: D* Lite（动态重规划更快但实现复杂度高，收益在频繁地图变更时才明显）；BFS（无启发式，200×200 下偏慢且路径质量差）。

## R3. 死锁避免与恢复

**Decision**: 三层策略——预防、检测、恢复。

1. **预防**：任务目标格下达前预约终点；规划时禁止把路径终点停在他车必经窄通道内（空闲车主动靠边不挡道）。
2. **检测**：车辆连续 N tick（折算 ~15s）位置未变且非正常等待终点 → 标记 `stalled`；多车互相构成等待环 → `deadlock` 候选。
3. **恢复**（按代价递增）：a) 受阻车重规划绕行；b) 让路——挡路空闲车收到让路指令，移向邻近空格；c) 改派——把任务回收重派给其他车；d) 兜底——虚拟"相位放行"（短暂冻结部分预约按序放行）。
- **Rationale**: "尽量避免 + 可自动恢复"符合规格（FR-012）；分层恢复保证多数冲突用最低代价手段解决。
- **Alternatives considered**: 全局死锁求解器/拓扑排序解锁：正确性证明复杂，演示场景收益低。

## R4. 任务生成与均匀分配

**Decision**: 双队列 + 最少负载优先（least-loaded）分配 + 随机抖动。

- 任务成对生成（1:1 入库/出库，FR-018）：出库任务随机选一个"有料箱的存储点位"，入库任务随机选一个"空存储点位"。
- 分配：每次选当前累计任务数最少的车（平局随机），数学上保证任意两车差 ≤1，远优于 ±20% 约束；同时任务点位随机散布。
- **Rationale**: least-loaded 是保证均匀性的最简构造，无需复杂均衡器。
- **Alternatives considered**: 纯随机分配（需要事后补偿才能满足 ±20%）；拍卖/竞标机制（过度设计）。

## R5. 仿真与前端通信架构

**Decision**: 单进程 asyncio 仿真引擎（固定 10 tick/s）+ FastAPI WebSocket 增量推送 + Canvas 2D 分层渲染。

- 引擎每 tick 产出增量（位置变化的车/箱、状态变化、指标），WS 下发 ≤100ms。
- 前端三层 Canvas：静态层（网格+货架+站点，只画一次）、障碍层（障碍物变更时重绘）、动态层（料箱+小车，每帧重绘）。
- 小车在格间移动做线性插值以获得连续高速观感（渲染层插值，逻辑层仍逐格）。
- **Rationale**: 单进程避免序列化/进程通信复杂度；增量推送使 100 车 @10tick/s 的带宽可忽略；分层 Canvas 保证 40k 格子下 ≥30fps。
- **Alternatives considered**: SSE/轮询（延迟与带宽差）；WebGL（40k 静态格 + 100 动态实体用不上）；多进程仿真（单机演示无必要，违背 YAGNI）。

## R6. 布局参数（固定布局，FR-016/FR-017/FR-021）

**Decision**: 200×200 地图按以下固定布局初始化：

- 货架区：地图中部，行 60..139 × 列 40..159。存储点位行与行、列与列之间均隔 **1 格通道**（点位行 60,62,..,138 共 40 行；点位列 40,42,..,158 共 60 列）= 2400 个存储点位（FR-021：1 格宽通道不加宽），半仓 ~1200 料箱；相向会车依赖让路机制（规格澄清项）。
- 入库口：地图西侧边缘中部（行 95..104，列 0..4 区域）；出库口：东侧边缘中部（行 95..104，列 195..199）。两站不同侧，车流自然分流。
- 充电区：南侧环场主干道内侧固定区域（默认行 185..193 × 列 85..114，可调），含 10 个充电位（一排）+ 独立进站/出站单向通道（进站口西侧入、出站口东侧出，避免与主线车流对冲）；与入库口/出库口错开（FR-016/FR-026，桩数核算见 R10）。
- 边界格不可通行；围墙内侧保留 2 格宽环场主干道。
- **Rationale**: 1 格宽通道保留高密度车流观感（规格澄清项，FR-021）；2400 点位提供充足的随机目标多样性，1200 料箱对渲染无压力（动态层仅绘制有料箱的点位）；充电区集中布置便于观察充电车流，单向进出站通道防止充电排队阻塞主干道。

## R7. 验证环境（docker rcs_core_dev）

**Decision**: 仿真本体为纯 Python + 浏览器，开发、测试与运行统一在容器内进行（2026-09-30 规格澄清：宿主机不作为运行环境）；容器内执行步骤写入 quickstart：
`docker exec -it rcs_core_dev bash -c "cd /home/dev/workspace/binglee/rcs_demo && ..."`
（host 网络模式，容器内启动的端口宿主机直接可访问）。
- **Rationale**: 容器为 host 网络，演示服务在容器内启动即可从宿主机浏览器访问；`--check` 自检不依赖 GPU/ROS，容器内直接可跑。

## R8. 测试策略

**Decision**: 缩尺快速回归（pytest）+ 演示级冒烟。

- 单元：A* 可达性/绕障、预约互斥、布局约束。
- 集成（缩尺 40×40 / 10 车 / 加速时钟）：跑 N tick 断言 ① 零同格碰撞 ② 分配偏差 ≤±20% ③ 注入围堵后 M tick 内恢复移动。
- 冒烟：`--check` 验证导入、布局生成、规划器自测、API 可绑定。
- **Rationale**: 200×200×100 车全量跑 30 分钟不适合 CI；缩尺模型与全量共享同一引擎代码，保证断言有效性。

## R9. 转弯软代价（直线偏好，FR-027）

**Decision**: A* 搜索状态从 `(row, col)` 扩展为 `(row, col, dir)`（dir ∈ N/E/S/W），移动代价 `g += 1 + TURN_PENALTY`（方向改变时加惩罚，默认 `TURN_PENALTY = 3`，可配置）。

- 曼哈顿启发式仍可直接使用（低估即可，保持可采纳性）。
- 状态空间 ×4，单次最坏 ~160k 节点；实际任务路径长度有限（~100 格），典型搜索远小于最坏值。以"每 tick 重规划次数限流 + 增量触发"控制 CPU（沿用 R2 策略）。
- 惩罚为软约束：转弯只是变贵、不禁止，可达性与 R2 完全一致；热点代价加权（R8/T050 的拥堵优化）在同一 g 函数上叠加，两者正交。
- **Rationale**: 直线偏好是路径代价层面的需求（FR-027 澄清项），方向感知 A* 是其标准最小实现；不引入路径后平滑（post-smoothing 会绕开预约检查，破坏零碰撞不变量）。
- **Alternatives considered**: 仅视觉平滑（不改变实际路径，不满足需求）；A* 后再对路径做拐角削减并重验预约（实现与验证成本高于方向感知搜索，收益相同）。

## R10. 电量模型与自动充电（FR-025/026/029，SC-010）

**Decision**: 车级电量状态机 + 充电区资源管理器，充电行程不占用 Task 队列。

- **耗电**：每移动 1 格扣电——空载 1 点、携带料箱 1.5 点（`BATTERY_FULL=1000`、`LOAD_FACTOR=1.5`，均可配置）；等待不耗电（演示简化）。
- **触发**：`battery < BATTERY_LOW_RATIO×BATTERY_FULL`（默认 20%）→ 标记 `need_charge`，**先完成当前任务**；任务完成瞬间派发"充电行程"（车级内部路径，目标是空闲充电位，经进站通道），优先级高于新任务分配——该车从可分配集合中移除。
- **充电**：占用充电位后按速率 `BATTERY_FULL / CHARGE_SECONDS` 回电（默认 30 秒从 20% 充到满）；达到返回阈值（默认 100%）→ 经出站通道离开 → 回到可分配集合。
- **排队**：10 个充电位全满时，`need_charge` 车在进站通道外指定排队格有序等待（电量更低者优先），不占主干道；电量降至 `BATTERY_CRITICAL_RATIO`（默认 5%）仍未获得车位时，完成当前移动段后直接前往充电区入口待命兜底——不出现电量归零趴窝。
- **核算**（FR-029 公式，参数联动）：忙碌桩数 ≈ 任务节奏 × 单任务平均耗电 ÷ 单桩充电速率 = 1×(100×1+100×1.5) ÷ (1000/30) ≈ 7.5 → 上取整 + 约 30% 余量 = **10 充电位**。任一参数调整按公式重算并在 `config.py` 联动提示。
- **Rationale**: 充电行程不走 Task 队列，避免污染 1:1 任务对与均匀性统计（completed_count 只计搬运任务）；状态机复用既有移动/等待/重规划机制，零碰撞约束天然成立。
- **Alternatives considered**: 充电占用 Task 队列（需在均匀性断言中剔除，容易引入偏差）；电量耗尽就地停摆等救援（与 SC-010"无电量耗尽停摆"冲突，弃用）。

## R11. 空闲车行为——取消漫游（FR-028）

**Decision**: idle 车停在最后任务完成位置（或初始位置）待命，不做任何无目的移动；仅有两种例外移动：a) 被死锁恢复机制要求让路（既有 `making_way` 语义，短距离避让）；b) 充电行程（R10）。

- 移除旧 wander 行为（tasks.md T013 实现的"idle 随机选目标闲逛"），替换为待命。
- **Rationale**: 漫游产生无意义车流、增加互堵概率，与 FR-028 冲突；就近待命还缩短下一次派单的空驶距离。
- **Alternatives considered**: 集中待命区（派单后空驶变长）；漫游待命（已被规格否决）。

## R12. 前端视口缩放与拖拽平移（FR-030）

**Decision**: 渲染层引入相机变换 `{scale, offset}`，与仿真逻辑完全解耦。

- **缩放**：滚轮以光标为锚点缩放，`scale ∈ [0.25, 4.0]`（`ZOOM_MIN/ZOOM_MAX` 可配置）；**平移**：按住左键拖拽移动 `offset`。
- **拖拽 vs 点击智能区分**：按下后位移 <5px 且时长 <300ms 判定为"点击"，走既有选中车辆/增删障碍物交互；否则为拖拽平移。无模式切换按钮。
- **默认视图与复位**：加载时 `scale` 取"整图适配窗口"值；工具栏提供复位按钮一键回整图。
- **性能**：动态层每帧仅绘制视口内实体（culling）；静态层预渲染到离屏 Canvas，视口变化时按 `{scale, offset}` blit——4× 放大下静态层有轻微缩放模糊，演示可接受。
- **Rationale**: 相机变换是纯展示层概念，不触碰仿真状态与预约逻辑，实现与回归风险最小；点击/拖拽阈值区分是地图类产品的通用惯例。
- **Alternatives considered**: 按缩放级别重绘静态层细节（清晰但实现复杂、违背 YAGNI）；模式切换按钮（交互多余，规格澄清已否决）。
